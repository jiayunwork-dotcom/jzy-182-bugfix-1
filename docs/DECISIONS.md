# 关键链排程与执行规则说明（DECISIONS）

本文件把题目中留给实现方决定的口径全部固定下来。后端代码严格按本文档
实现，且这些规则都保证**确定性**：同一份输入，无论谁提交、提交多少次、
服务是否重启过，计划与状态都逐项一致。

---

## 1. 计划阶段：资源冲突消解与关键链识别

### 1.1 输入

* 任务网络：任务 id、名称、紧前任务、资源需求（资源 id → 数量）、
  激进工期 `agg`、保守工期 `cons`（单位：工作日，允许 0，不允许负数，
  `agg <= cons`）。
* 资源：id、名称、可用总量（容量）。
* 所有调度计算只使用**激进工期**；保守工期只用于推算缓冲。

### 1.2 资源消解规则（确定性 Serial-SGS）

1. 计算每个任务的**下游权重**
   `w(t) = agg(t) + max(w(s) | s 是 t 的逻辑后继)`，即从该任务出发
   沿逻辑依赖最长的一条激进链长度（包含自身）。
2. 用带优先队列的 Kahn 过程生成一个满足紧前关系的优先级表：
   每一步在所有"紧前已排定"的任务中，选择 **`(-w, 任务 id)` 最小**者
   （等价于：下游最长链更长者优先；等长时 id 字典序小者优先）。
3. 按此优先级表逐个放置任务（Serial Schedule Generation Scheme）：
   * 候选开始时间 = 所有紧前完成时间的最大值，以及"当前占用其所需资源、
     容量不足"的每个占用区间的结束时间；
   * 在这些候选时刻中选择最早的、使任务整个执行区间内每种资源占用
     都不超过容量的时刻。

**直观解释**：离终点最远的那条分支先抢资源；同长则 id 靠前的先抢。

### 1.3 关键链

排定每个任务的开始/完成时间（工作日单位，项目起点为 0）后，构造一张
**紧边图**，其边为：

* 逻辑紧边：`p -> t`，若 p 是 t 的紧前且 `finish(p) == start(t)`；
* 资源紧边：任务 t 在时刻 `start(t)` 需要资源 r 才能启动，若没有恰好在
  该时刻释放出来的占用量，t 在该时刻无法启动，则每一个"恰好在
  `start(t)` 完成、且占用 r"的任务 i 都有 `i -> t` 边。

**关键链 = 紧边图上按激进工期加权的最长路径**（总时长等于排程工期
makespan）。

* **无资源冲突时**，不会产生资源紧边，紧边图上的最长路径就是只看逻辑
  依赖的关键路径，二者完全一致（有测试覆盖）。
* **等长链的确定性裁决**：若多条路径总时长相等（误差 ≤ 1e-9 工作日），
  选**任务 id 序列字典序最小**的一条。裁决是按路径自终点回溯、逐级对
  前驱链做 `(长度, id 元组)` 比较完成的，因此不是只比较首尾任务。
* 所有浮点比较使用容差 1e-9；输入为整数工期时结果为精确整数。

### 1.4 该规则会在什么网络上偏长（启发式的已知弱点）

这是一个"最长下游优先"的贪心规则，**不保证资源受限下的最短工期**。
已知会偏长的典型结构：

* 多个任务共用一种资源、先散开再合并（diamond / fan-out-fan-in）网络。
  规则永远先放行下游更长的分支；如果先做短分支反而能让两个分支更好地
  穿插（短分支先完成、在长分支执行期间由别的资源/间隙消化），本规则会
  反过来安排，得到一条比最优排程更长的关键链。
* 资源种类多、且不同资源的瓶颈任务分布不一致时，单一权重无法同时兼顾。

它的可取之处是：规则简单、可解释、稳定（同输入永远同输出），且永远不
短于纯逻辑关键路径——也就是说不会漏掉真实存在的冲突代价。若需要更短
排程，可以把优先级表换成枚举/分支定界，接口与后续缓冲、投影模块完全
不变。

题目给定算例在该规则下的结果：`A(4)` 后 `B(w=8)` 先于 `C(w=5)` 占用
工程师，C 被推到第 10 天，链为 **A → B → C → D = 15 工作日**。

### 1.5 汇入缓冲（Feeding Buffers）的识别

对每个关键链节点 v，找它的每个（逻辑或资源）前驱 p 中不属于关键链的，
在"非关键链节点子图"上取以 p 结尾的最长路径，作为一条汇入路径。同一
路径只产生一个缓冲（按汇入的 CC 节点位置、路径长度、id 元组去重排序）。

## 2. 缓冲大小的推算口径

采用经典 CCPM 的 **50% 截尾法（cut-and-past / RSEM 的线性版本）**：

```
PB = 0.5 × Σ(conservative − aggressive)          （关键链上每个任务）
FB = 0.5 × Σ(conservative − aggressive)          （每条汇入链上每个任务）
```

* 选择依据：保守−激进是各任务自带的安全时间区间；把整条链上的安全时间
  削掉一半、集中放在链尾，是关键链法的标准做法——既利用了任务级不确定性
  的聚合效应（缓冲不必等于各任务余量之和），口径又足够简单、可审计。
* 没有引入额外的分布假设（如 lognormal 的 2 分位/9 分位法），因为输入里
  只有两个点估计；一旦工期为整数，缓冲就是 0.5 的整数倍、无舍入误差。
* **放置**：PB 放在链尾 `[makespan, makespan + PB]`；FB 按经典 Goldratt
  位置放在汇入链最后一个任务结束处（`end = finish(链尾任务)`），缓冲末端
  到关键链节点之间若有间隔，是该汇入链天然拥有的**计划松弛**，甘特图上
  直观可见。缓冲不改变任务排程与 makespan（即采用"非侵入式"放置）。
* **同比缩放性质**：所有工期同乘正整数 k 时，下游权重、优先级表、紧边图
  拓扑关系、关键链形状都不变；makespan、各缓冲大小恰好乘以 k
  （有测试覆盖）。

## 3. 执行阶段：汇报流语义

### 3.1 追加式日志与幂等

* 汇报只追加（`reports` 表，主键 `(project_id, report_id)`），从不改写或
  删除历史。
* 同一汇报编号重复提交：`INSERT OR IGNORE`，第二次返回 `duplicate=true`，
  状态不变（幂等，有测试覆盖）。

### 3.2 早到 / 迟到汇报：一律"插回正确位置重算"

状态永远是汇报流按下述**全序**排序后的一次纯折叠（fold）：

```
排序键 = (汇报时刻 at, 汇报编号 report_id)
```

* 汇报时刻早于最近记录时，**不拒收**，而是插入到正确位置，全量重放
  重算。同一时刻多条汇报用 report_id 字典序决出唯一顺序，因此排序是全序，
  不存在"两条并列"的可能。
* 任务级状态取折叠后该任务的**最后一条**汇报的效果：`done`（或
  remaining=0）→ 已完成；否则进行中，剩余工期取该汇报值。历史全部保留，
  只是投影结果变化——后续更新的汇报仍会覆盖较早的汇报。
* 乱序到达与按时刻顺序逐条到达，最终状态**逐项相等**（纯函数，有测试
  覆盖）。
* 两个项目经理并发提交：写入由 SQLite 事务 + 写锁串行化；无论写入如何
  交错，最终折叠所用的仍是同一条按 `(at, report_id)` 排序的逻辑流，所以
  最终状态与串行逐条提交一致（多线程并发测试覆盖）。

### 3.3 关键链冻结，不随进度重识别

采用**冻结关键链**策略：计划一旦创建，执行阶段使用的就是冻结时的关键链；
汇报只改变"链完成比例"和"缓冲消耗"，链的形状不随单次汇报跳动。范围/
网络真的变了，应当新建计划（新项目/新基线）。

对发烧图曲线的影响：

* 曲线**稳定、单调可比**：每个点都落在固定的 0–100% 坐标系里，历史点永不
  因后续汇报而位移（历史回放就是排序流前缀的折叠，逐字段相等，有测试）。
* 代价是可能**过时**：若实际中某条非关键链被拖成真正的瓶颈，冻结视图不会
  把它"提拔"为关键链，风险通过该汇入路径的 FB 消耗体现；当大量 FB 同时
  穿透而 PB 尚低时，用户应据此判断需要重排基线。
* 备选方案（每次汇报重排）的曲线会因关键链变化而在横轴上跳变、历史点
  不可比，故不采用。

### 3.4 工作日历

* 1 个工作日 = 周一至周五 09:00–18:00（9 个工时），周末不承载工作量；
  暂不含节假日（可在 `app/worktime.py` 扩展节假日表）。
* 时刻在窗口外会吸附到下一个有效工作时刻（18:00 整是合法的日末时刻）。
* 排程本身以"工作日"为单位做纯数值计算，绝对时间只在展示与汇报投影时
  通过该日历换算。

## 4. 状态投影与发烧图

### 4.1 关键链完成比例

```
已得工期 = Σ 已完成 CC 任务的 agg + Σ 进行中 CC 任务的 (agg − remaining)
完成% = 已得工期 / Σ(CC 任务 agg)
```

### 4.2 项目缓冲消耗（穿透）

对每条链（关键链或某条汇入链），逐任务比较计划完成与"预计完成"：

* 已完成任务：预计完成 = 实际完成时刻；
* 进行中任务：预计完成 = 当前时刻 + 汇报的剩余工期；
* 未开始任务：不计入（不假设它已延误）。

`穿透天数 = max(0, 预计完成 − 计划完成)` 在链上取最大值（链末端的最大
拖累）。`缓冲消耗% = 穿透 / 缓冲大小 × 100`。PB 为 0 时记 0%（无穿透）或
100%（有穿透）。消耗可以超过 100%（发烧点画在 100% 线上方，区域仍为红）。
每条汇入缓冲在状态接口里给出各自的消耗%。

### 4.3 发烧图分区

每个项目设置两条**水平分界线** yellow_pct / red_pct（纵轴方向）：

* 消耗 < 黄线：绿区；黄线 ≤ 消耗 < 红线：黄区；≥ 红线：红区。
* 约束：`0 ≤ 黄 < 红 ≤ 100`，违反则以字段级错误拒收。

每条汇报产生一个轨迹点（坐标=当时的链完成%、PB 消耗%，并携带当时各任务
剩余工期快照）。查询任意历史时刻 `?at=`，等价于只回放到该时刻为止的
汇报，返回与该轨迹点逐字段相同的状态。

### 4.4 持久化与重启恢复

* SQLite（WAL 模式）两张表：`projects`（规范化输入 + 计划 JSON）、
  `reports`（追加流，自增 seq）。
* 状态不在任何地方缓存，每次请求从汇报流现算；重启后直接读库即可恢复，
  无需重建步骤。重启前后 `/state` 与 `/fever` 输出相等（有测试覆盖）。
* 数据库文件位于挂载卷（默认 `/data/ccpm.db`，可用 `CCPM_DB_PATH` 覆盖）。
